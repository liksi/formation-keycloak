Keycloak Practical Work

PW 1 - Configure authentication on a webapp

Goal
  • Discover the lab platform
  • See the most common authentication techniques in action

In this exercise, we will deploy a simple webapp and test multiple authentication mechanisms. The webapp has two pages:

  • A publicly accessible home page
  • A page containing sensitive data that requires protection

This webapp is built with Spring Security, Spring Boot and Maven. No prior knowledge of these tools is required.

1. Start secret-webapp

  • git clone https://github.com/liksi/formation-keycloak.git
  • cd formation-keycloak/secret-webapp
  • mvn spring-boot:run

NB: the application starts on port 8090

  • On your Lab, find your machine’s public URL. Its should be something like x2xrtsjbaemmuis5y-gsshzf7apajysewiz.labs.strigo.io

  • open a browser and go to your machine URL on port 8090 (http://x2xrtsjbaemmuis5y-gsshzf7apajysewiz.labs.strigo.io: 8090).

  • Click on the link to go to the protected page.

    • Check that there is no protection configured

2. Enable basic authentication

  • Comment the line authentication-mode: none and uncomment #authentication-mode: basic
  • restart the webapp (Ctrl-C + mvn spring-boot:run)
  • use curl to fetch the secret page
    • curl http://localhost:8090/secret/index.html -v
    • Note that a 401 status code is returned (Unauthenticated vs Forbidden)
    • Note that there is a WWW-Authenticate header, meaning that the app is expecting an Authorization header.
    • use -u flag to set the username and password
      • Look into FormConfig.java to see what is the expected user and password
    • Note how a Authorization header is added in the request
  • now use the browser to reach the secret page
    • authenticate on the native browser popup
    • open the developer console of your browser and see how the password is sent on every request.

3. Enable form-based authentication

  • use curl to fetch the secret page
    • curl http://localhost:8090/secret/index.html -v
    • What does the returned status mean ?
  • use the browser to login
    • use the dev console to visualize the session cookie (named JSESSIONID)
    • what does the “HttpOnly” attribute mean ?
  • use -b flag to inject the cookie in the curl request
    • curl http://localhost:8090/secret/index.html -v -b JSESSIONID=YOUR_COOKIE_VALUE
    • note that the whole security relies on the fact the JSESSIONID cookie cannot be stolen
  • Restart the server and redo the curl request with the JSESSIONID cookie
    • What happens ? Can you explain it ?

PW 2 - OpenID Connect Protocol

Goal
  • Manipulate OIDC requests and tokens
  • Use SSO
  • Understand where sessions are stored

In this exercise, we will use an existing Keycloak instance hosted on cloud-iam (a Keycloak-as-a-service provider).

1. Forge OIDC requests with curl

  • Have a look at all the OIDC-related endpoints exposed by Keycloak https://lemur-5.cloud-iam.com/auth/realms/keycloak-training/.well-known/openid-configuration
    • Which OIDC flows can be used to generate a token ?
    • What is the URL that must be called to generate a token ?
  • craft an OIDC request with curl to generate an access token using “direct_grant” flow:
    • curl https://lemur-5.cloud-iam.com/auth/realms/keycloak-training/protocol/openid-connect/token -v -d grant_type=password -d client_id=curl -d username=test -d password=pwd
  • Use jwt.io to inspect token content
    • What are the 3 colors used for ?
    • What is the user email ? did Keycloak verify this email ?
    • Was the token signature verified by jwt.io? Where does the displayed key come from ?
  • Use OIDC to refresh the token
    • curl https://lemur-5.cloud-iam.com/auth/realms/keycloak-training/protocol/openid-connect/token -v -d grant_type=refresh_token -d client_id=curl -d refresh_token=YOUR_REFRESH_TOKEN
    • inspect the new token and compare it with the previous one. What is the session_state claim ?
  • use your access token to request the /userinfo endpoint
    • curl https://lemur-5.cloud-iam.com/auth/realms/keycloak-training/protocol/openid-connect/userinfo -H “Authorization: Bearer YOUR_ACCESS_TOKEN”
    • What happens (use curl -v to see error details) ?
  • add the “openid” scope in the curl request that generates the first accessToken (-d scope=openid)
    • What happens ?
    • Compare the content of the access token & id token
    • Get userinfo
      • curl https://lemur-5.cloud-iam.com/auth/realms/keycloak-training/protocol/openid-connect/userinfo -H ‘Authorization: Bearer YOUR_ACCESS_TOKEN’
      • Compare the JSON payload with the idtoken content
  • try to generate tokens using authorization code flow (grant_type = authorization_code)
    • What happens ? What is the code Keycloak is talking about ?

2. Configure secret-webapp to delegate authentication to Keycloak

  • Open file src/main/resources/application.yml to enable Keycloak-based auth
    • Restart the app and try to access the secret page (don’t login)
      • What happens ?
  • Open the Network tab of the developer console and login
    • Do you see a request /token ? why ?
    • Refresh the page
      • Explain the requests you see
    • Restart your server and refresh the page
      • Explain the requests you see
  • From the secret page, click on logout
    • What are the states of the session on Keycloak and on the webapp ?
    • navigate to https://lemur-5.cloud-iam.com/auth/realms/keycloak-training/account
      • This page is exposed by keycloak to let users manage their personal data
      • What happens if you login on this page and then navigate to the secret page ?
      • What happens if you logout from the webapp and then refresh the account app ?

Extra activities

Try to use revocation & introspection endpoints of Keycloak

PW 4 - Keycloak installation

Goal

See what it looks like to run Keycloak without Docker and understand what needs to be configured.

0. Stop the Docker Keycloak service

  • cd keycloak
  • docker compose down

1. Start Keycloak with “dev mode”

  • Go to Keycloak website to get the download url (zip file). Use wget to download the file from your “Lab”
  • unzip
  • bootstrap an admin user and run dev mode
    • export KC_BOOTSTRAP_ADMIN_USERNAME=admin && export KC_BOOTSTRAP_ADMIN_PASSWORD=secret && bin/kc.sh start-dev
    • You should see Keycloak startup logs
  • Open a browser on the port 8080 of your lab
    • Open http://YOUR_URL:8080/admin/
    • If you are reaching the lab through a public HTTP URL and still see “HTTPS required”, open a shell in another tab and run:
      • bin/kcadm.sh update --server http://localhost:8080 --realm master --user admin --password secret realms/master -s sslRequired=NONE
    • This time you should be able to access the admin pages.

2. Start Keycloak with “production mode”

  • Dev mode should not be used for production:

    • No reliable database (H2)
    • No control of the hostname used to generate tokens
    • No clustering

  • To start Keycloak without dev mode, you need to provide at least

    • the public URL where it can be accessed from the outside
    • the permission to use http instead of https (we don’t want to manage keys & certs now) => DON’T DO THIS IN PRODUCTION !
    • bootstrap admin credentials
    • example : export KC_BOOTSTRAP_ADMIN_USERNAME=admin && export KC_BOOTSTRAP_ADMIN_PASSWORD=secret && bin/kc.sh start --hostname=http://your-lab-host:8080 --http-enabled=true

  • Make sure you still can access Keycloak

  • Note that there are lots of really good official guides for Keycloak configuration https://www.keycloak.org/guides

    • Look for example how you could configure Keycloak to use a Postgres database

3. Clustering

  • in another shell (open a new tab in the Lab) start another instance of Keycloak on a free port
    • Same command as before with a different HTTP port, for example --http-port=8081
    • Use another hostname/port pair and point both instances to the same Postgres database
  • Look at Keycloak logs and see how the two instances communicate together to create a cluster and share data.
  • Stop the first instance
    • Look at the logs of the 2nd instance and see how infinispan detects a new topology

4. Metrics and logs

  • Start Keycloak with following parameters
    • –health-enabled=true
    • –metrics-enabled=true
    • –log-console-output=json
  • User curl to see what information are exposed on the paths below
    • curl http://localhost:9000/metrics
    • curl http://localhost:9000/health/ready
    • curl http://localhost:9000/health/live
  • Why do you think there are two distinct paths for healthcheck ?
  • See how logs are now formatted in JSON. This can be useful to integrate with log aggregation tools

PW 5 - Securing a “modern” app (SPA + API) with Keycloak

Goal

Know how to use Keycloak to manage authentication in an architecture based on public clients (SPA or mobile apps) and APIs.

1. Securing a Java API with Spring OAuth Resource Server

  • Start the REST API
    • cd api

    • docker compose up -d
  • Use curl to fetch the two resources below
    • curl http://localhost:8091/messages/public
    • curl http://localhost:8091/messages/admin -v
    • Why does Springboot returns 401 instead of 403 ?
  • Configure Keycloak and change api/src/main/resources/application.yml accordingly to protect the API with your own instance
    • Why don’t we need to configure a client id / client secret ?
    • NB: the following documentation lists all the configuration parameters for oauth resource servers: https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server /jwt.html
  • Create a client named ‘curl’ with direct grant enabled. Use this client to generate an access token

    • curl http://<Lab url>:8080/realms/<your_realm>/protocol/openid-connect/token -v -d grant_type=password -d client_id=curl -d username=test -d password=pwd

    • Use a user with no pending required actions and a non-temporary password.

    • use this access token to fetch http://localhost:8091/messages/admin If access is denied, look into api/src/main/java/fr/liksi/formation/keycloak/resourcepr ovider/config/OauthResourceConfiguration.java to understand what is missing

      • Warning, Spring Security by default considers that roles are prefixed with ROLE_*. Consequently, “ADMIN” role in Springboot must be named “ROLE_ADMIN” in Keycloak

    • Why do you think role management configuration is complex (see jwtAuthenticationConverter method) when the rest of the configuration seems fairly straightforward ?

    • Look at Spring app logs and search in the code how to get access to user data stored inside the token

      • Change the code to log user email
  • Modify OauthResourceConfiguration.java to grant access to http://localhost:8091/messages/user to any user having ADMIN or USER role
    • You can use hasAnyRole() method, which takes a list of roles, e.g. hasAnyRole(“Dev”, “Tester”)

PW 6 - Keycloak in an Enterprise Information System

Goal

Set up the features you most commonly need when integrating Keycloak into an existing enterprise system.

Prerequisite: Start your own Keycloak instance and use it to protect the secret-webapp application (same setup as PW 3).

  • Test that accessing the secret page requires authenticating on Keycloak
  • Test that logout redirects the user to secret-webapp homepage

1. Events journal

  • Start Keycloak with docker compose (see PW 3)
  • In the Events tab, configure the events you want to store in the database, as well as the retention policy
  • Observe the events that are created when users log in or when you perform administrative actions (user creation, …)
  • Do you think this is a good way to monitor Keycloak?

2. Connect Keycloak to an LDAP server

In this part, we will simulate that our users are managed in a LDAP server inside the company. We will configure Keycloak to use this LDAP store instead of its own database.

1. Setup an LDAP server

  • Start openldap and an admin UI
    • cd keycloak
    • docker compose up -d
  • Navigate to https://YOUR_HOST:6443 (ignore SSL warnings)
  • Authenticate with the following credentials
    • login : cn=admin,dc=formation
    • password: admin
  • Create a new group:
    • “Create New Entry” > Generic: Posix Group
    • Set name = users (or whatever name you want)
    • Submit and Click on Commit
  • Create some users
    • “Create New Entry” > Generic: User Account

2. Connect Keycloak to the LDAP server

  • Go to the Admin console > Tab “User Federation”
  • Select “Add Provider” > LDAP
  • Select “Other” as Vendor
    • All pre-filled parameters are correct
  • Fill-in connection parameters
    • URL : ldap://openldap
    • Users DN : dc=formation
    • Bind DN : cn=admin,dc=formation
    • Bind Credential : admin
    • EditMode = READ_ONLY
  • Click on “Test connection” and “Test authentication”. Everything should be ok
  • Click on “Action (top-right of the page) > Sync all users” and check that all your LDAP users have been imported
  • Check that you can login with these users on the secret-webapp

3. Advanced configuration: synchronization

  • In Keycloak, go to the Mappers tab of your LDAP connector

  • Select EMAIL mapper and turn off the READ-ONLY flag

  • In the LDAP connector configuration page, try the different values of EDIT MODE parameter

    • Try to update one of your users email from Keycloak and check what happens in LDAP
    • Do you understand what happens for READ_ONLY, WRITABLE and UNSYNCED modes ?

  • Look at “Sync Settings” parameters from your LDAP connector.

    • What are those fields used for ?

4. Advanced configuration: role mapping

In LDAP, user permissions are encoded using groups (just as what is done in Linux). Granting permissions to a user is equivalent to assigning a user in a group.

  • In your LDAP server, create a new group (New entry > Posix Group)
  • Assign some of your users to this group
  • In Keycloak, add a mapper on your LDAP connector in order to map LDAP groups to Keycloak roles.
    • Be careful, some default values of the mapper are wrong ! Look at the group definition inside LDAP to fix these parameters.
    • Do a full resync and check that the imported users have the right permissions.

3. Use a third-party Identity Provider

In this part, you will:

  • Register an external Identity Provider on your Keycloak
  • Create a client on your Keycloak so that someone else can use your instance as an IdP

For this exercise, we simulate a setup where Keycloak instance 1 is a provider for instance 2, and vice-versa — not something you would typically do in real life, but a great way to understand the mechanism.

1. Create a confidential client for the other Keycloak instance

  • create a confidential client for your colleague
  • Share the client_id / client_secret with him/her

2. Register the other Keycloak instance as an Identity Provider

  • Go to “Identity Providers” Tab and create a new provider with type “Keycloak”
  • Configure the connection URLs of the other Keycloak instance
  • Configure the clientId / client secret you should have received at previous step
  • Submit

3. Login with the external Identity Provider

  • When you try to login from your webapp, you can now see a button linking to the other Keycloak
  • Use one of the users created on the other Keycloak instance to authenticate

4. Role mapping

The roles configured on the other Keycloak instance are not automatically converted into roles on your instance. - Configure a mapper that will “translate” roles from other Keycloak into a role of your own instance - Remove the user and retry to login. You should see that roles have been imported.

NB: notice that the user is really inserted into your local database. Once the user has logged in, he/she has her own lifecycle inside your Keycloak instance.

5. User merging (optional)

  • Remove the identity provider link on the user imported during the login process
    • User details > Identity Provider Links
  • Set a password to this user
  • Try to login using the external IdP using this user
    • What happens ?
  • Change the login flow to trust the data coming from the IdP and not ask anything from the user

4. Use an authenticating Reverse Proxy

We will use OAuth2-proxy (https://oauth2-proxy.github.io/oauth2-proxy/) and Keycloak to protect access to a website that does not provide any authentication.

1. Start secret-webapp without any security

  • cd secret-webapp
  • Edit src/main/resources/application.yml and set authentication-mode: none
  • mvn spring-boot:run
  • Check that you can access private content

2. Keycloak configuration

  • create a confidential client named “oauth2-proxy”
  • copy the secret
  • add an audience mapper on this client so tokens contain oauth2-proxy as audience

3. OAuth2-proxy configuration

  • cd keycloak
  • edit docker-compose.yml
  • configure

    • OAUTH2_PROXY_CLIENT_ID => your client id

    • OAUTH2_PROXY_CLIENT_SECRET => your client secret

    • OAUTH2_PROXY_OIDC_ISSUER_URL => Keycloak URL (including realm)

    • OAUTH2_PROXY_REDIRECT_URL => Oauth2 proxy URL

    • OAUTH2_PROXY_UPSTREAMS => URL of the service you want to protect

    • In Clients > oauth2-proxy > Client Scopes, make sure the default client scope roles is still assigned to the client.

  • docker compose up -d Try to access your lab on port 4180. You should be redirected to Keycloak. If this doesn’t happen, check the logs (docker logs oauth2-proxy)

4. Authorization on the proxy

Sometimes we want to add extra checks before authorizing access.

  • Uncomment the line #OAUTH2_PROXY_ALLOWED_ROLES: "MANAGER"
  • Change OAUTH2_PROXY_EMAIL_DOMAINS value to "keycloak.org"
  • Try to fix your user configuration to regain access

  • Test that accessing the secret page requires authenticating on Keycloak

2. Customize the login page theme

Your product owner would like to change the title on the login page. She suggests: ”Dear user, please login to access this page”.

3. Add a custom protocol mapper

Your product owner wants a new feature available only to adults. You will need to store the user's age as a Keycloak attribute and add a mapper that sets a boolean claim ”is_adult” in the idToken.

4. Add a custom authenticator (secret question)

Your product owner wants to improve security by adding a “secret question” step during the authentication flow.

4.1. Collect a secret question & answer from the user

This step will be implemented with a custom “RequiredAction”. This action is triggered by Keycloak after authentication if specific conditions are met. In this case, this condition will be that the user has an empty “question” attribute.

  • Before testing this part, open Realm Settings > User Profile and enable unmanaged attributes for the training realm. Otherwise those attributes are not stored.

  • Open src/main/java/…/requiredaction/UpdateQuestionAction.java

    • In the “evaluateTriggers” method, fix the condition to trigger the RequiredAction only when the “question” attribute of the user is empty. You can use the methods below:
      • StringUtil.isBlank(“XXX”) returns true iff XXX is empty
      • context.getUser() retrieves current user
      • user.getFirstAttribute(“XXX”) returns the value of the XXX attribute of a user

  • In the “processAction” method, fix the initialization of answer and question vars

    • Look at update-question.ftl template to understand how answer and question should be initialized
    • formData.getFirst(“XXX”) returns the value of the parameter XXX of the form

  • Store the answer and the question in user attributes

    • context.getUser().setSingleAttribute(“attrName”, value);

  • open messages/messages_en.properties and create all the messages required by the template (you can also try without setting the messages and fix after)

  • Uncomment the line in resources/META-INF/services/org.keycloak.authentication.RequiredActionFactory to register the RequiredAction

  • Rebuild the extension

    • cd provider
    • mvn clean package

  • Rebuild docker image and start

    • docker compose build
    • docker compose up -d

  • Enable the required action in realm configuration

    • Authentication > Required Actions
    • If the provider first appears in the “Unregistered” list, click Register before enabling it.

  • Test ! => Keycloak should request a secret question as part of the first login
